# 第六章投资结论与批量结构迁移

## 适用场景

- 将旧报告的“投资结论”和独立“总结”合并为新版第六章。
- 批量统一同一项目内多份投资分析报告的章节结构。
- 只调整报告组织，不重做前文研究、评分、估值或数据日期。

## 目标结构

```markdown
## 六、投资结论

### 6.1 商业模式好不好（Right Business）
#### 6.1.1 业务简单可持续、不易被替代
#### 6.1.2 竞争格局清晰、护城河深厚、有定价权
#### 6.1.3 轻资本投入、高资产回报率、自由现金流好
#### 6.1.4 有长期增长空间

### 6.2 管理层怎么样（Right People）
### 6.3 是不是好价格（Right Price）
### 6.4 胜率与赔率
### 6.5 长期持有检查项
### 6.6 评级与行动

## 七、投资逻辑与证伪条件
## 八、维度打分汇总
## 九、数据校验结果
```

不再保留独立“总结”章。第六章只归纳前文已经论证的事实，不增加新评分、新估值或新事实。

## 内容映射

1. 原总结中的四项商业模式判断移入6.1，并将编号改为6.1.1—6.1.4。
2. 原总结中的管理层判断移入6.2。
3. 原总结中的当前价格判断移入6.3。
4. 原投资结论中的胜率和赔率合并到6.4。
5. 原长期持有检查移入6.5。
6. 原评级、行动建议和最终判断移入6.6。
7. 原第七章投资逻辑、证伪条件和第八章评分原则上只改必要编号，不改内容。
8. 删除迁移后为空的独立总结章，将数据校验调整为第九章。

## 变体处理

- **旧投资结论没有子标题**：将核心判断放入6.4；把后续验证条件放入6.5；把当前动作放入6.6。不得因结构迁移扩写新的研究结论。
- **旧总结没有四项固定标题**：只能从该报告前文已有事实中归纳6.1—6.3，并保持原报告的数据日期与口径；不能照搬另一日期版本的数据。
- **评分表混在投资结论中**：移动到第八章，避免第六章重复打分。
- **存在额外专题章**：不得删除。若它属于好时机的延伸，可作为5.x专题保留；再让投资结论回到第六章。其他专题按内容选择相邻章节或顺延，但必须说明处理方式。
- **报告后有资料来源章**：数据校验固定为第九章，资料来源可顺延为第十章；无编号的“主要来源”可以保持不变。
- **多个日期版本**：用户要求“当前目录下全部报告”时全部迁移；只要求最新报告时，按公司保留历史版本不动。

## 安全执行顺序

1. 先盘点全部目标文件及六至十章标题，不直接批量写入。
2. 按结构变体分组：标准四节投资结论、无子标题投资结论、额外专题章、缺少评分章、旧总结无固定结构。
3. 先做只读转换预演，检查每份报告预期的新章节列表。
4. 只替换报告后半部分相关章节，保留前五章、评分数字、图表和来源。
5. 抽查至少四种变体，再执行全量结构校验。
6. 不顺手修改Skill、项目框架、README、脚本或历史数据；除非用户分别明确要求。

## 批量校验

每份报告至少验证：

- 6.1—6.6各出现一次且正文非空；
- 6.1.1—6.1.4各出现一次且顺序一致；
- 不存在独立总结章；
- 第八章为评分汇总，第九章为数据校验；
- 四模块得分之和等于总分，评级未被结构迁移改变；
- Markdown代码块闭合，无重复章节分隔线；
- 所有本地图片链接真实存在；
- 第六章数字和判断均能在前文找到依据；
- 有公司专用 `verify_report.py` 时运行并要求 `all_ok: true`；
- 最后运行 `git diff --check`，并抽查标准报告、无子标题报告、额外专题报告和历史旧版报告。

## 常见错误

- 只改章节编号，却仍让第六章和独立总结重复表达。
- 把所有旧行动建议都塞入“长期持有”，导致“评级与行动”只剩一句话。
- 为了凑齐6.1—6.3，从另一版本或外部资料引入新数据。
- 删除额外专题章，或者让专题章占用第六章导致投资结论继续顺延。
- 批量迁移时顺便改Skill、项目框架、README或评分，扩大用户确认的范围。
